# 02 — 技术架构设计

- 版本：v0.1
- 日期：2026-11-22
- 状态：草案
- 关联：`01-PRD-产品需求规格.md`、`05-技术选型与决策记录.md`

## 1. 架构目标

1. 每个目标窗口独立捕获，互不影响。
2. 捕获、检测、UI 解耦；核心状态机可脱离真实窗口测试。
3. 默认本地、无网络、无截图落盘。
4. 权限缺失时降级，不阻塞其他目标。
5. 先做可构建的 Swift Package 骨架，M1 再补正式 `.app` 打包与签名。

### 2.1 模块边界

| 模块 | 位置 | 责任 | 禁止 |
|---|---|---|---|
| `ArgusCore` | `Sources/ArgusCore` | 模型、协议、纯状态机 | import SwiftUI/AppKit；发起网络 |
| `Argus` app | `Sources/Argus` | SwiftUI、ScreenCaptureKit、Vision、Accessibility、AppKit | 直接改写检测器内部状态 |
| `CaptureCoordinator` | M2c 暂不拆分 | 原计划独立协调器；M2c 评估后仍由 `DashboardStore` 承载，等 M3 检测管线接入再决定是否抽离 | 为拆分而拆分；把帧写磁盘 |
| `DashboardStore` | M1 新增 | UI 状态与命令编排；M1–M2a 暂兼捕获会话生命周期与目标列表 | 在后台线程改 UI |
| `WindowActivator` | M2 新增 | 激活目标窗口 | 猜窗口；激活无关应用 |
| `PermissionManager` | M1 新增 | 权限查询、引导、热更新 | 静默降级不提示 |
| `TargetFileStore` | M2a 新增 | 持久化版本化文件、原子写、损坏隔离 | 落盘截图或窗口正文 |
| `TargetRestorer` | M2a 新增（ArgusCore） | 重启解析：唯一窗口才绑定，多候选不猜 | 用标题/位置猜窗口 |

## 3. 捕获设计

### 3.1 目标解析

1. 用 `SCShareableContent` 枚举可共享窗口。
2. 过滤 Argus 自己的窗口、桌面、菜单栏等非目标窗口。
3. 用户选择后，保存：
   - `bundleIdentifier`
   - `windowTitle`（用于重启后匹配）
   - 显示尺寸/位置快照（仅用于识别，不作为身份主键）
4. 同一应用多窗口：每张卡片绑定一个 `SCWindow.windowID`；窗口 ID 变化时用标题+尺寸重新解析，解析不唯一则标记“待重新选择”。

### 3.2 捕获会话

每个目标一个 `WindowCaptureSession`：

```text
SCContentFilter(desktopIndependentWindow: window)
SCStreamConfiguration:
  width: 448 (or window aspect)
  height: proportional, max 1440
  minimumFrameInterval: 1.0s (M4 calibrated)
  queueDepth: 3
  showsCursor: false
  capturesAudio: false
SCStream(output: sampleHandler)
```

- 只保留最新帧；队列满时丢旧帧，不无限堆积。
- 捕获帧转 `CGImage` 后：
  - 生成缩略图（建议 320×180 或等比）；
  - 送入检测管线（可降采样）。
- `stop()` 必须释放 `SCStream`、移除 output、停止计时器。

#### 3.2.1 M2c 生命周期语义

- **暂停**：停止该目标的 `SCStream`，保留最后一帧作为带 `PAUSED` 标记的静态快照；暂停期间不接收新帧，恢复后重新开流。
- **窗口关闭**：轮询用 `CGWindowList` 复核绑定窗口 id；消失即进入 `WINDOW CLOSED`，不是终态。后台每 10 秒重试，按 §3.1 的严格唯一规则重绑；同 bundle 多候选或零候选继续等待，不猜。
- **竞态**：启动、恢复、重绑、暂停、移除都在 `MainActor` 串行；`SCStream.start()` 返回后再次核对目标仍在列表、窗口 id 未变、未暂停，否则立即 `stop()`，不挂载过期会话。
- **暂停与重建**：暂停目标不参与自动重建；恢复时先查原绑定窗口 id，失效才走严格匹配。

### 3.3 不可捕获状态

需要显式处理并上报：

- 屏幕录制权限被拒；
- 窗口关闭 / 应用退出；
- 窗口最小化或被系统隐藏（是否可捕获需实测）；
- 受保护/DRM 内容返回黑帧；
- 多显示器切换、Space 切换、显示器休眠；
- 目标窗口全屏时是否仍按窗口捕获。

UI 不得在不可捕获时继续显示旧缩略图当作实时画面。

## 4. 检测设计

### 4.1 信号提取（M3 实现）

每个目标一个 `ReplySignalAnalyzer` actor，只保存上一帧灰度网格、上一轮文本哈希、上次 OCR 时刻、OCR 可用状态、最新 prompt 下界和视觉 Stop 状态。帧与 OCR 文本都是局部变量，返回观测后立即释放。

| 模块 | 位置 | 责任 |
|---|---|---|
| `LumaGrid` | `ArgusCore/Detection` | 160×160 灰度网格与像素变化比例；尺寸不一致返回 nil |
| `TextFingerprint` | `Argus/Detection` | 归一化空白/大小写后生成 SHA-256；不保留正文 |
| `ReplySignalAnalyzer` | `Argus/Detection` | 融合视觉变化、文本指纹、可选 AX 信号，输出 `ReplyObservation` |
| `AXStopControlProbe` | `Argus/Detection` | 绑定进程内唯一标题窗口，查找 enabled Stop-like `AXButton` |
| `ReplyProfile` | `ArgusCore/Detection` | ROI、control ROI、settle、OCR 间隔、阈值、置信度门槛 |

`ReplyObservation`：

| 字段 | 含义 |
|---|---|
| `textFingerprint` | 目标区域文本的稳定哈希，不是正文 |
| `textRegionEmpty` | OCR 成功但回答区为空；用于重置短回复基线 |
| `newPrompt` | 最新右侧用户 prompt 下移；即使回复与旧回复相同也算新一轮 |
| `isChanging` | 与上一采样相比回复区域是否变化；nil = 未测量 |
| `hasGeneratingIndicator` | 是否观察到 Stop/Generating 控件；true 为强信号 |
| `confidence` | 信号置信度 |
| `source` | visual / accessibility / fused |

首版策略：

1. **视觉基线**：捕获 1 fps；Dashboard 每 0.25 秒轮询但只发布新帧做帧差；窗口存在性 1 Hz；OCR 只在首帧、OCR 失败恢复、或画面确有变化且超过 `ocrInterval` 时执行。静态完成窗口不持续烧 Vision。
2. **OCR**：Vision `.fast`、`usesLanguageCorrection=false`、`en-US` + `zh-Hans`，仅本地；只保留哈希。豆包等右侧气泡客户端只对最新 prompt 下方的回答文本做哈希；空回答区或新 prompt 会重置生成基线。
3. **Accessibility 增强**：仅检查目标窗口所属进程；窗口标题按 `WindowMatchPolicy` 唯一匹配；最多 600 节点、深度 8。`true` = 可见 enabled Stop，`false` = 树可见但没有 Stop，`nil` = 权限/窗口/树不可用。没权限不崩溃，视觉继续工作。
4. **Profile**：按 `bundleIdentifier` 配置 ROI、control ROI、settleDuration、ocrInterval、阈值。`ReplyProfile.generic` 的 `controlROI=nil`，因此不会把回复正文里的 “stop” 误当 Stop 控件。
5. **融合**：`hasGeneratingIndicator == true` 为强信号，直接按 generating；文本变化为 generating；OCR 不可用时降置信度按 unknown，不用像素硬判完成；视觉 Stop 关键词只在配置了 control ROI 时启用。M3 不做多数投票，冲突时以 generating / unknown 保守处理。

### 4.2 状态机

核心实现：

`Sources/ArgusCore/Detection/ReplyCompletionDetector.swift`

```text
generating -> streaming
idle (after generating) -> settling
settling + stable >= settleDuration -> completed
generating again (from settling/completed) -> streaming
signal unavailable / low confidence -> unknown
```

关键不变量：

- 没有 `generating` 历史时，`idle` 不会直接变成 `completed`。
- `completed` 后只有新的 `generating` 才能重新打开。
- `unknown` 清空 settle 计时，但保留「曾观察到 generating」历史；短暂 OCR 失联不会永久阻止后续完成。
- settleDuration 默认 1.0 秒；Profile 可覆盖，但必须在 fixture 中验证。
- 生成开始后回答文本必须相对基线增长（或出现新 prompt/空回答区后的第一段文本）；只有 prompt、思考动画或旧回复残留不得进入 `completed`。
- `phaseChangedAt` 只在 phase 真正变化时更新；UI 用它显示最近状态时间。

### 4.3 误判控制

- 高置信才显示 `Completed`；文本信号缺失时降 `Unknown`，不伪造完成。
- 每个应用 Profile 至少有一个正例、一个负例 fixture。
- 对“长时间停顿但仍在生成”的模型，允许把 settleDuration 提高到 2–3 秒；`stall` / `stallAx` fixture 专门覆盖。
- 记录状态转换时间线；fixture 事件日志只记生命周期标签与时间戳，不记正文。

## 5. 窗口切换

### 5.1 激活策略

1. 用 `NSRunningApplication` 按 bundleIdentifier 找到目标进程；未运行返回 `targetNotRunning`。
2. 已授予 Accessibility 时，先读取 `AXUIElement` 窗口标题，按 `WindowMatchPolicy` 匹配，再激活：
   - 唯一匹配，或应用只有一个窗口：激活应用并 raise 该窗口；
   - 多个匹配：返回 `ambiguousWindows`，**不激活应用**，避免把用户带到错误窗口；
   - 无匹配：返回 `windowNotFound`。
3. 未授予 Accessibility：只激活应用，返回 `applicationOnly(.accessibilityNotGranted)`，UI 明示“只切到了应用”，不宣称已切到目标窗口。
4. 标题只作匹配提示：空标题不能消歧；重复标题视为不唯一；标题变化后需用户重选。
5. UI 显示失败或降级原因，不静默。

### 5.2 多窗口

- 卡片保存目标窗口身份；窗口 ID 变化后按标题重新解析（尺寸匹配属候选增强，未实现）。
- 解析不唯一时要求用户重新选择，不自动绑定。
- 多显示器下优先激活包含目标窗口的显示器/Space；具体行为在 M2 实测。

## 6. 权限

| 权限 | 用途 | 缺失时 |
|---|---|---|
| Screen Recording | ScreenCaptureKit 捕获 | 无法捕获；显示引导 |
| Accessibility | 读取控件/窗口层级、raise 窗口 | 降级为纯视觉检测；切换可能只能激活应用 |

- 权限状态变化要监听并热更新。
- 首次请求前给出用途说明；拒绝后提供系统设置入口。
- 不把权限请求和“开始捕获”混在一次点击里，避免用户不知道授权了什么。

## 7. 数据与隐私

- `TargetApplication` 可持久化：bundle id、标题匹配、卡片顺序、Profile id。
- 不持久化：截图、缩略图、OCR 文本、对话正文、提示词。
- 诊断日志只记录：时间、目标 id、状态、错误码、耗时；正文脱敏。
- MVP 无网络代码；若未来增加更新检查/遥测，必须新 ADR，并默认关闭。
- 崩溃报告若启用，必须确认不含窗口内容。

## 8. 并发与性能

- `DashboardStore` 在 `MainActor`；捕获与检测在独立 actor/队列。
- 每个目标独立限流；单目标卡顿不阻塞其他目标。
- 目标数量上限触发资源保护：硬上限 3，拒绝新增并提示；暂停/恢复由用户手动执行（M2c），不做自动暂停最久未活跃卡片。
- 帧队列有界；只保留最新帧用于缩略图。
- OCR 频率低于帧率；先帧差，再决定是否 OCR。

## 9. 测试缝

- `CaptureSource` 协议：测试注入 `MockCaptureSource`，回放帧序列。
- `ReplyCompletionDetector` 纯状态机：单元测试，无 UI/无窗口。
- `WindowActivating` 协议：测试注入 `MockActivator`，验证失败路径。
- `PermissionManager` 协议：测试注入 granted/denied/unknown。
- 真实捕获只在手工/集成环境验证；CI 不请求系统权限。

## 10. 阶段实现顺序

1. **M1**：窗口枚举、权限、单目标 `SCStream`、一张真实缩略图。
2. **M2**：多目标协调、卡片状态、点击激活、持久化。
3. **M3**：OCR/帧差/Accessibility 信号、Profile、检测 fixture。
4. **M4**：背压、资源上限、异常恢复、诊断、4 小时稳定性。
5. **M5**：`.app` 打包、签名、公证、内测分发。

## 11. 开放架构问题

- ScreenCaptureKit 对最小化/被遮挡窗口的实际行为。
- 是否需要独立的 XPC/Helper 进程隔离捕获崩溃。
- 多目标 OCR 的 CPU 成本是否可接受；是否需要按目标降采样/ROI。
- 窗口身份在重启后的稳定匹配策略。
- 是否需要 App Sandbox；若上架 App Store，ScreenCaptureKit/Accessibility 能力是否满足审核。
- `one-code` 检测模块 2026-11-22 评估后暂不直接复用，仅记录思路；见 `09-立项与能力迁移.md`。
