# 05 — 技术选型与决策记录

- 版本：v0.1
- 日期：2026-11-21
- 状态：Accepted / Proposed 混合，逐条标注

## ADR-001 macOS 首版使用 SwiftUI 原生应用

- **状态**：Accepted（2026-11-21）
- **决策**：首版只做 macOS，使用 Swift 6 + SwiftUI，最低 macOS 14。
- **理由**：
  - 需要 ScreenCaptureKit、Accessibility、NSRunningApplication 等系统能力；原生栈最短。
  - 多窗口捕获与激活对系统 API 的依赖高，Electron/Tauri 会增加一层跨平台抽象。
  - Argus 是个人 macOS 工具，不需要首版跨平台。
- **代价**：Windows 迁移需要另起实现；UI 不能直接复用 Web 组件。
- **替代方案**：Electron + desktopCapturer；Tauri + Rust；均暂不采用。

## ADR-002 使用 ScreenCaptureKit 作为捕获层

- **状态**：Accepted（2026-11-21）
- **决策**：M1 使用 `SCShareableContent` + `SCStream` 按窗口捕获。
- **理由**：
  - 支持按窗口过滤，不需要截取整个屏幕。
  - 与 macOS 的屏幕录制权限模型一致。
  - 可以控制帧率、队列深度、是否采集音频/光标。
- **代价**：权限敏感；受保护内容/最小化窗口行为需要实测。
- **替代方案**：`CGWindowListCreateImage`（旧 API，能力受限）；全屏截图后裁剪（隐私与性能都差）。

## ADR-003 本地优先，不上传屏幕内容

- **状态**：Accepted（2026-11-21）
- **决策**：MVP 不包含任何主动网络请求；不持久化截图、OCR 正文、对话内容。
- **理由**：
  - 屏幕内容可能包含密钥、客户数据、私人对话。
  - 本地运行能显著降低合规与信任成本。
  - 首版不需要账号、云同步或远程监控。
- **代价**：不能跨设备同步；不能远程查看。
- **例外**：未来若加更新检查/遥测/云同步，必须先写新 ADR，默认关闭并明确告知。

## ADR-004 完成检测采用多信号 + Unknown，不伪造完成

- **状态**：Accepted（2026-11-21）
- **决策**：
  - 视觉帧差/OCR 文本稳定性作为基础信号。
  - Accessibility 与 Stop 控件作为增强信号。
  - 任一强信号冲突或缺失时输出 `unknown`。
  - 只有高置信才显示 `completed`。
- **理由**：不同 AI 客户端 UI 差异大；单信号极易把“停顿”误判为“完成”。宁可漏报，不可误报。
- **代价**：部分场景会显示 Unknown；需要人工标注与 Profile 迭代。

## ADR-005 Dashboard 以“每个目标一张卡”为基本单位

- **状态**：Accepted（2026-11-21）
- **决策**：一个目标窗口 = 一张监控卡片；同一应用多窗口 = 多张卡片。
- **理由**：用户心智是“这个窗口的回复完成了吗”，不是“这个应用完成了吗”。多窗口必须可区分。
- **代价**：需要稳定的窗口身份解析；卡片数量多时要有资源上限。

## ADR-006 M0 先做 Swift Package，M1 再补正式 `.app`

- **状态**：Accepted（2026-11-21）
- **决策**：当前仓库用 Swift Package 提供可构建骨架；M1 补 app bundle/Info.plist/签名验证。
- **理由**：先让核心状态机与文档可测试；避免一开始被 Xcode 工程文件与签名阻塞。
- **代价**：Swift Package executable 不是完整 `.app`；权限与分发必须在 M1/M5 重新验证。
- **注意**：不得把 `swift run` 的可用性当成正式分发可用性。

## ADR-007 Argus 归入 BayJF Tier 2

- **状态**：Accepted（2026-11-21，owner 已在 catalog 定级）
- **决策**：Argus 是 Tier 2 一般项目，中优先级、按需推进。
- **影响**：
  - 不抢占 Tier 0/1 的主线资源。
  - 先做本地可用 MVP，不追求首版大规模推广。
  - BayJF catalog 已登记 `argus`；Tier 规范需同步。

## ADR-008 MVP 不单独建 `argus-landing`

- **状态**：Proposed（2026-11-21，建议默认执行，owner 可改）
- **决策**：
  - 不为 Argus 新建独立 `argus-landing` 仓库。
  - MVP 的公共入口使用 BayJF 的 `/products/argus` 与 `/zh/products/argus` 产品页/案例页。
  - 不在 Argus 代码仓里塞营销落地页；产品仓只放代码、PRD、架构和发布文档。
  - 等 M4/M5 有真实界面证据、外部用户和独立品牌需求后，再评估是否建 `argus.bayjf.com` / `argus-landing`。
- **理由**：
  - Argus 目前是 Tier 2、M0 骨架，没有可展示的真实界面，独立 landing 内容不足。
  - 现有 landing 收敛策略明确“不为新项目新开子域”；26 个子域维护面已经很大。
  - 产品页与案例页能复用 BayJF 的 SEO、导航、双语与分析基线。
- **代价**：Argus 没有独立品牌首页；早期只能从 BayJF 产品目录进入。
- **未来拆分触发条件**：默认长期留在 BayJF 产品页；只有同时满足至少 3 项才拆为独立 landing：
  - 需要公开下载、版本更新、支持/法律页，BayJF 案例页已承载不了。
  - 出现独立品牌搜索、外部合作、投放或独立转化目标。
  - 有持续的教程、对比、FAQ、更新日志等 SEO 内容。
  - 能独立承担子域部署、分析、内容维护与法务页成本。
- **拆分后的边界**：`argus-landing` 独立仓 + Cloudflare Pages + `argus.bayjf.com`；BayJF `/products/argus` 保留为作品集案例页，两处避免复制同一篇正文，canonical 各自指向自身。
- **复核点**：M4 内部 Alpha 后，若出现独立品牌搜索/外部合作/需要独立下载页，再开新 ADR。

## ADR-009 首版不做云同步/远程监控

- **状态**：Accepted（2026-11-21）
- **决策**：不做账号、云同步、远程查看、团队共享。
- **理由**：与本地隐私定位冲突；首版价值在单机多窗口监控。
- **代价**：不能跨设备；后续若要做，需重新设计权限、加密与合规。

## ADR-010 目标应用 Profile 不进入核心状态机

- **状态**：Accepted（2026-11-21）
- **决策**：Profile 只提供 ROI、控件特征、settleDuration 等参数；状态转换仍由 `ReplyCompletionDetector` 统一执行。
- **理由**：避免每个应用一套私有状态机，导致不可测试、不可比较。
- **代价**：极端 UI 可能需要额外信号，但也要以 `ReplyObservation` 形式接入。
